# PLC interpreter: design

Status: phases 1 (ladder) and 2 (Structured Text) built: `site/js/plc.js`, `tools/plc-tests.mjs` (68 tests), `tools/output-checks/plc/`. Every ladder and Structured Text lesson (50 ladder, 48 Structured Text) has a scenario and a generated output. Where one rewrites the other, `sameAs` holds their traces identical (24 pairs). Phase 3 (browser simulator) built: a Simulate panel on every PLC lesson with a scenario runs the learner's own code, with inputs from the scenario, a live tag table, energized paths drawn green, and the Conveyor 3 jam-cell scene on the track steps that build that cell. Phase 4 built: generic scenes (Conveyor 3 jam cell, Hoop Driver 1 air header, Char Station 2 burner and fan), "Compare with the reference" (behavioral check of the learner's code against the scenario), and two challenge lessons, "Stop on low air" and "Purge before and after the flame". Structured Text stage 2 built: arrays, `FOR`/`WHILE`/`REPEAT`/`EXIT` and `ABS` (see Arrays and loops below). Not built yet: `CTUD` (see open questions).

## Why

Two problems, one piece of code.

1. **Outputs for PLC lessons are hand-written.** The PLC & HMI track's ladder and Structured Text steps show cause-and-effect traces ("Eye blocked 4.0 s while running → Jam_Timer.DN=1 → Jam_Fault=1") that nobody generated by running the code. That breaks the rule every other language now follows, and it is why the Ladder and Structured Text lanes cannot reach 50 lessons with outputs.
2. **The simulation goal.** The learner's own typed rungs should drive a small piece of equipment on screen, so a change to the logic makes a visible difference.

Both need the same thing: a program that runs ladder and Structured Text the way a Logix controller scans it.

## Goals

- Run the ladder and Structured Text the lessons use, with Logix semantics close enough that a trace from the interpreter matches what a learner would see in Studio 5000 for the same inputs.
- One implementation, used in three places: the verifier and output tool in Node, and the trainer in the browser. Same rule as `core.js` today: grading in CI matches grading in the browser, and now simulation does too.
- Deterministic. The same code and the same scenario always give the same trace, so outputs can be checked in CI.
- No dependencies, no build step.

## Non-goals

- Not a PLC emulator. No I/O modules, tasks, periodic or event scheduling, produced/consumed tags, Add-On Instructions, UDT editing, online edits, faults beyond the few the lessons teach, or communications.
- No safety meaning. A rung that behaves correctly here proves nothing about a real machine. The UI and docs say so.
- No Ignition scripting. Ignition steps keep hand-written outputs until a separate stand-in for `system.*` exists.

## What it must support

Taken from the current lessons (19 ladder lessons, 3 Structured Text lessons), plus what the Structured Text lane will need next.

| Area | Instructions and features |
|---|---|
| Ladder: bits | `XIC` `XIO` `OTE` `OTL` `OTU` `ONS` |
| Ladder: branches | `BST` `NXB` `BND`, nested, on the input or output side |
| Ladder: timers | `TON` `TOF` `RTO`, members `.EN` `.TT` `.DN` `.ACC` `.PRE` |
| Ladder: counters | `CTU` `CTD` `RES`, members `.CU` `.CD` `.DN` `.OV` `.UN` `.ACC` `.PRE` |
| Ladder: compare | `EQU` `NEQ` `GRT` `GEQ` `LES` `LEQ` `LIM` |

## Semantics

The point of the interpreter is to get these right, because they are what the lessons teach.

**Scan cycle.** Each scan: apply the scenario's input changes for this moment, evaluate every routine's rungs or statements top to bottom, advance the clock by the scan time. Tags update immediately, so a later rung sees what an earlier rung wrote in the same scan. That is what makes the seal-in and the "later rung wins" state-code lesson work. Real Logix I/O updates asynchronously to the scan; here inputs change only between scans, which keeps traces repeatable. The difference is noted wherever it could matter.

**Rung condition.** Every ladder instruction receives rung-condition-in and returns rung-condition-out, as in the Rockwell instruction reference.

- Input instructions (`XIC`, compares, `ONS`) pass out the AND of rung-in and their own test.
- Output instructions pass rung-in through, so outputs can sit in series or in parallel legs.
- A branch evaluates each leg with the same rung-in; the branch's rung-out is the OR of its legs.
- Output instructions run on false rungs too, where Logix defines behavior: `OTE` writes 0; `TON` resets; `TOF` starts timing; `CTU` and `CTD` update their edge bits. `OTL`, `OTU`, `MOV`, `ADD` and `CPT` do nothing on a false rung.

**Edges.** `CTU` counts when rung-in is true and `.CU` was false on the previous scan, then sets `.CU` to rung-in. `CTD` the same with `.CD`. `ONS` uses its storage bit the same way. This is what the corrected "Count barrels" lessons say: `CTU` needs no one-shot.

**Time.** A simulated clock in milliseconds, advanced by a fixed scan time per scan (default 10 ms, set per scenario). Timers accumulate the scan time. Nothing reads the computer's clock, so traces never vary.

**Numbers.** `DINT` is a 32-bit integer and wraps on overflow, setting the overflow flag. `REAL` is stored with `Math.fround` so it has the same 32-bit precision as a Logix REAL. `CPT` evaluates in REAL when any operand is REAL. The exact integer rules (rounding when a REAL lands in a DINT, and integer division) must be checked against the Logix instruction reference, 1756-RM003, before they are coded. See open questions.

**Tags.** A tag is created the first time a lesson or scenario uses it, with its type inferred from context: a timer instruction makes a `TIMER`, a member like `.DN` implies its parent's type, a value written by `MOV` or `CPT` takes the type of its value, anything used as a contact is `BOOL`. A scenario can declare types explicitly where inference is ambiguous. A lesson never has to declare tags, matching how the lessons read today.

**Arrays and loops (Structured Text).** Arrays are one-dimensional `BOOL`, `DINT` or `REAL`, declared by the scenario (`types: { History: "REAL[5]" }`) because nothing in the code gives their size. Elements are numbered from 0. An index outside the declared size stops the run with an error, because a Logix controller takes a major fault there rather than ignoring the write. `FOR` works out its end and step once before the first pass, includes both ends, and leaves the loop variable one step past the end; `BY 0` is refused. `WHILE` tests before each pass, `REPEAT` after, so a `REPEAT` body always runs once. `EXIT` leaves the innermost loop. Loops run inside one scan, as on a controller; a loop past 100,000 passes stops with a watchdog message instead of hanging the page. `ABS` keeps the type of its argument. Whether Logix stops evaluating `AND` early is not relied on: no lesson reads an array element whose index the same expression has just checked.

## Scenarios: how outputs get generated

A ladder or ST lesson that should show an output gets a `sim` field: the inputs to apply over time and the tags to report. For the current "Jam detection" step it would look like:

```js
sim: {
  scanMs: 10,
  start: { Auto_Mode: 1, Estop_OK: 1, Conv_Run: 1 },
  steps: [
    { label: "Eye blocked 4.0 s while running", set: { Eye_Blocked: 1 }, runMs: 4000 },
    { label: "Reset_PB while eye still blocked", pulse: { Reset_PB: 1 }, runMs: 100 },
    { label: "Reset_PB with eye clear", set: { Eye_Blocked: 0 }, pulse: { Reset_PB: 1 }, runMs: 100 },
  ],
  watch: ["Jam_Timer.DN", "Jam_Fault", "Run_Permissive", "Conv_Run"],
}
```

After each step the runner prints the step's label and the watched tags that changed during it, in the same "→" style the hand-written outputs use, so learners see a familiar format. A step where nothing changed prints "no change". The trace becomes the lesson's `out`, generated and checked like every other output:

- `tools/output-checks/plc/run.mjs` writes the outputs, with `--check` to report stale ones, the same as the Foundations runner.
- The verifier runs every scenario in CI and fails if the stored output no longer matches the code.

A track step's scenario runs against all earlier steps in the same routine, the way a track's earlier code already shows as context.

## Structure

| File | Contents |
|---|---|
| `site/js/plc.js` (new) | Pure code, no DOM. Exposes `BCplc`: ladder tokenizer and parser, ST tokenizer and parser, runtime (tag table, scan, instruction set), scenario runner, trace formatter. Loaded in `index.html` after `core.js`; loaded by the verifier through `vm`, like `core.js`. |
| `site/js/app.js` | The ladder diagram switches to `BCplc`'s parser, replacing its regular expression, so the drawing and the interpreter can never disagree. Later: the simulator panel. |
| `tools/verify.mjs` | Parses every ladder and ST lesson (catching unknown instructions, unbalanced branches, missing semicolons, ST syntax errors, which nothing checks today) and runs every `sim`. |
| `tools/plc-tests.mjs` (new) | Instruction-level tests, one per behavior above, written from the instruction reference. Run by the verifier. |

The parser produces a tree that both the runtime and the diagram use. The current diagram regex reads any three capitals followed by a parenthesis as an instruction, and stops an argument list at the first `)`, so a `CPT` expression with parentheses would break it. No lesson does that yet, but the CPT lessons will.

Expected size: `plc.js` about 700 to 900 lines; simulator UI about 300 lines added to `app.js` and `app.css`.

## Simulator in the browser (later phase)

Below the ladder diagram, a Simulate panel:

- **Inputs:** a button per boolean input (momentary for pushbuttons, latching for switches) and a slider for analog values such as `Hoop1_Air_PSI`.
- **Controls:** run, pause, single scan, speed (1×, 10×), reset.
- **Rung highlighting:** energized paths drawn in the status green, as in Studio 5000's online view.
- **Watch table:** live tag values, including timer and counter accumulators.
- **Equipment view:** an SVG scene bound to tags. First scene: the Conveyor 3 jam cell, with barrels moving on the belt, the photo eye, the motor running, and the jam light. Later scenes: the Hoop Driver 1 air header and Char Station 2's burner and exhaust fan, matching existing lessons.

It runs the learner's own typed logic, starting when the step is finished or Check is pressed, the same rule as the Plant Board's JavaScript preview, so half-typed rungs never run. Colors follow the design tokens: green, amber and red for status only.

## Risks

- **Fidelity.** A subtle difference from Logix would teach the wrong thing, which is worse than no simulator. Mitigation: instruction tests written from the instruction reference, and every lesson trace reviewed before it ships. Ideally, spot-check a few scenarios against a real controller or Studio 5000 emulation if you have access.
- **Scope creep.** Each new lesson will want one more instruction. Mitigation: the instruction table above is the scope; additions are deliberate.
- **Learner confusion with real PLCs.** Mitigation: the simulator states it is a teaching model and lists what it leaves out.

## Open questions for review

0. **CTUD on FBD_COUNTER.** Deferred: the meaning of its `.CU`/`.CD` outputs versus its stored edge state needs confirming in 1756-RM003 before it is modeled. No lesson uses it yet.
0. **RES on a counter.** The model clears `.ACC`, `.DN`, `.OV` and `.UN` and keeps `.CU`/`.CD`. Whether Logix also clears `.CU`/`.CD` decides whether a counter whose input is still on counts again right after a reset. Confirm in 1756-RM003; no scenario depends on it yet.
1. **Integer rules.** How does Logix round a REAL into a DINT destination, and what do `DIV` and `CPT` give for integer division? These must come from 1756-RM003, not memory. Do you have the manual or a controller to confirm against? Until then the interpreter refuses these cases with a `NotModeled` error instead of guessing.
2. **Output format.** Keep the "label → changed tags" lines the current outputs use, or switch to a time-stamped table (time, input change, tag values)? The lines read better; the table is more precise.
3. **Scan time.** 10 ms by default, matching the "a scan takes a few milliseconds" explanations in the lessons. Change it per scenario where a lesson is about scan timing?
4. **First scene.** The Conveyor 3 jam cell is proposed because the PLC track already builds its logic. Would a different machine be more useful to you or your friends?
5. **Ignition.** Ignition script and expression lessons also have hand-written outputs. A separate stand-in for `system.tag` and `system.db` could generate them later. In scope after phase 2, or not?
